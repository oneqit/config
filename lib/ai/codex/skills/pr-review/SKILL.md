# PR 리뷰 — 여섯 관점 + before/after 페이지

결과물은 **로컬 HTML 페이지 하나**다: 맨 위에 이 PR 이 코드의 동작을 어떻게 바꾸는지 before/after 그림, 그 아래 여섯 관점의 지적.
지적은 확인된 결함만, 지금 얼마나 아픈지와 고칠 길까지. 개수를 채우지 않는다 — 관점에 낼 것이 없으면 "없음" 한 줄.

## 1. 맥락과 흐름 파악 (직접)

- PR 본문 · 커밋 · diff, 프로젝트 지침(CLAUDE.md · 규약), 관련 **설계 문서**, 본문이 가리키는 연관 PR · 티켓의 실제 상태
- 이미 달린 리뷰 — 같은 지적을 또 내지 않는다. 다시 리뷰면 지난 리뷰 이후 커밋만
- **변경이 닿는 흐름**을 진입점 → 처리 → 저장소 · 외부 호출로 적는다. base 에서 한 번, head 에서 한 번. 이것이 before/after 그림의 재료이고, 2단계에서 "diff 밖 기존 코드" 를 어디까지 볼지 정한다
- **영향받는 API** — 바뀐 코드에서 호출자를 거슬러 올라가, 그 코드를 거치는 API(HTTP · gRPC 엔드포인트, 메시지 컨슈머처럼 밖에서 부르는 진입점)를 모은다. diff 에 컨트롤러가 없어도 공유 부품이 바뀌면 그것을 쓰는 API 가 모두 대상이다. API 마다 호출자에게 달라지는 것(요청 · 응답 모양, 상태 코드 · 오류, 동작, 지연)을 적는다
- **주장 목록** — diff 가 더하거나 고친 문서 · PR 본문 · 주석 · KDoc · API 설명(Swagger)에서 확인할 수 있는 말을 뽑아 적는다: 동작, 숫자, 이름(잡 · 명령 · 경로 · 설정 키), 단정("늘" · "항상" · "~뿐" · "~한 적 없는"). 관점 1 · 5 의 재료다
- **형제 코드** — 새로 생긴 클래스 · 테스트 · 테스트 헬퍼마다 같은 층의 형제(다른 서비스 · 컨트롤러 · 테스트 클래스, 테스트 지원 디렉터리)를 둘 이상 읽고, 형제가 공통으로 하는 것(로그 · 커밋 뒤 처리 · 공용 헬퍼 · 단언 방식)을 적는다. 흐름 밖이어도 읽는다 — 관점 4 · 5 · 6 의 재료다
- 작업 트리를 바꾸지 않는다 — 다른 커밋은 `git show <sha>:<path>`, 실행은 스크래치 worktree

## 2. 여섯 관점

| # | 관점 | 핵심 질문 |
|---|---|---|
| 1 | **설계 · 본문 · 주석 ↔ 구현** | 설계 문서 · PR 본문 · 주석 · KDoc 이 말하는 동작과 숫자가 코드 · 설정과 같은가? 본문의 배포 · 복구 절차를 지금 코드로 따라가면 그대로 되는가? |
| 2 | **기능 구멍 · 버그** | 어떤 입력 · 순서 · 실패에서 틀린 결과 · 멈춤 · 조용한 누락이 나는가? |
| 3 | **성능** | 지금은 괜찮아도 데이터가 10배 · 100배일 때 — 잠금 · 인덱스 · 쿼리 계획 · 메모리 · 타임아웃 · 반복 호출이 어떻게 되는가? |
| 4 | **중복 · 미사용 코드** | 같은 규칙이 여러 곳에 있거나, 변경으로 쓰이지 않게 된 코드 · 설정 · 테스트가 남았는가? 새로 더한 것이 레포에 이미 있는가? **고칠 가치가 있는 것만** |
| 5 | **테스트 빈칸** | 바뀐 동작마다 유닛 테스트가 **정상 · 실패(예외 · 거부 · 재시도) · 엣지(빈 값 · 경계 · 중복 · 큰 입력)** 케이스를 갖췄는가? 있는 테스트는 그 규칙이 깨지면 실패하는가? 빠진 케이스를 동작 단위로 적는다 |
| 6 | **더 맞는 패턴** | 레포의 기존 관용구에 더 맞는 모양이 있는가? 형제가 다 하는데 새 코드에만 없는 것이 있는가? 없거나 판단이 서지 않으면 쓰지 않는다 |

**관점마다 거르지 않는 절차** — 표의 질문에 답하기 전에 한다. 한 것과 결과를 템플릿의 그 관점 **기록 칸**에 한 줄씩 채운다. 지적이 없어도 기록 칸은 채운다.

- **관점 1** — 주장 목록을 하나씩 코드와 맞춘다. 이름은 레포에서 검색해 실제로 있는지 본다. 단정에는 반례를 하나 대 본다(같은 요청을 두 번 · 실패 경로 · 동시 요청). 같은 주장이 여러 문서에 있으면 서로 어긋나지 않는지 본다
- **관점 4** — 새로 더한 함수 · 테스트 헬퍼는 이름과 하는 일로 레포를 검색해 이미 있는 것과 겹치는지 본다. 같은 설명이 문서 · 주석 여러 곳에 반복되면 한 곳에만 두자는 지적을 `선택` 으로 낸다
- **관점 5** — 차례로 한다
  - **뮤턴트 정하기** — 새로 생기거나 바뀐 테스트마다: 테스트 이름이 말하는 규칙을 지키는 줄, 주장 목록이 그 동작에 대해 말한 속성(되돌림 · 유지 · 거절)을 지키는 줄, 검증 제약이 여럿이면 제약 하나하나. 그 줄을 되돌렸을 때(어노테이션 제거 · 조건 뒤집기 · 순서 바꾸기) 테스트가 통과하면 그 테스트는 규칙을 지키지 않는다
  - **돌리기** — 테스트가 동시성 · 잠금 · 트랜잭션 경계 · 검증 제약을 다루면 뮤턴트를 실제로 돌린다. 같은 줄을 되돌리는 뮤턴트는 한 번만 적용해 테스트 클래스를 돌리고 그 결과를 여러 테스트에 쓴다. 돌리지 못했으면 방법을 읽기로 적고 이유를 남긴다. 그 밖의 테스트는 단언을 읽어 어떤 뮤턴트가 살아남는지 적는다. 어느 쪽이든 단언이 형제 테스트만큼 구체적인지 본다
  - **빠진 테스트** — 테스트가 아니라 주장 목록과 새 코드를 따라가며 본다. 테스트가 아예 없는 것이 여기서 나온다: 주장 목록의 속성마다 그것을 단언하는 줄이 있는가, 새 코드가 속한 모듈에 그 테스트가 있는가(다른 모듈의 테스트가 간접으로 덮으면 그렇게 적는다). 본 것마다 기록 표에 한 행을 적는다 — 테스트 칸에 그것을 지키는 테스트, 없으면 「없음」
- **관점 6** — 1단계에서 적은 형제의 공통점 중 새 코드에 없는 것을 낸다. 없는 이유가 코드 · 주석 · 문서에 적혀 있으면 지적으로 내지 않고 기록 칸에 그 이유를 적는다

**근거의 기준** — 가능하면 로컬에서 재현한다(테스트 실행, 규칙 한 줄을 되돌린 뮤턴트, 컨테이너 DB 에 쿼리, 숫자는 직접 계산). 재현하지 못하면 코드 경로를 끝까지 따라간 근거를 적고, 코드 밖 사실에 달린 것은 질문으로 낸다. 어떤 방법으로 확인했는지를 지적마다 남긴다.

**"문제없음" 으로 닫기 전에** 반례를 하나 시도한다 — 같은 코드를 다른 각도(실패 경로 · 종료 신호 · 큰 데이터 · 동시 요청)로 한 번 더 본다. 이 판정이 가장 많이 틀렸다.

**나눠 보기** — 파일이 많거나 흐름이 여럿인 PR 은 서브에이전트를 띄울 수 있으면 관점 1 · 2 · 3 · 5(필요하면 4)를 병렬로 돌린다. 각자에게 1단계에서 적은 흐름 · 주장 목록 · 형제 코드 메모 · 그 관점의 절차 · 브리프 파일 경로 · 위 표의 그 관점 한 줄 · 근거의 기준 · 결과 파일 경로를 준다. 결과 파일에는 지적과 함께 그 관점의 기록 행도 적게 한다. 서로 다른 스크래치 경로를 주고, 재현에 띄운 worktree · 컨테이너는 지우게 한다. 관점 6 과 그림은 지휘자가 마지막에 직접 한다. 작은 PR 은 혼자 차례로 본다.

## 3. 심각도

| 표기 | 기준 |
|---|---|
| `높음` | 데이터 손실 · 권한 구멍 · 조용히 틀린 결과 · 정상 입력으로 오류 · 그대로 따라 하면 잘못 동작하는 운영 절차 · 다음 배포가 기동하지 못함 |
| `중간` | 지금 경로에서 조건만 맞으면 닿는 결함 · 문서 · 계약과 다른 동작 · 핵심 규칙을 지키는 테스트가 없음 |
| `낮음` | 아직 없는 기능 · 데이터 규모가 와야 닿는 결함 · 테스트 약점 · 틀린 주석 · 낡은 문서 |
| `선택` | 하면 좋은 정리 · 패턴 |
| `결정 필요` | 코드가 아니라 사람이 정할 것 |

머지를 막을 것(코드)과 배포 전에 할 것(본문 · 절차 · 인프라)을 구분해 결론에 적는다.

## 4. 결과 페이지

`assets/report-template.html` 을 레포 밖 임시 디렉터리(예: `${TMPDIR:-/tmp}/pr-review-<번호>/review.html`)에 복사해 채운다. 다 쓰면 파일 경로를 알려 주고, macOS 면 `open <파일>` 로 브라우저에 연다. 외부 서비스에 올리지 않는다.

그림은 인라인 `<svg>` 로 손으로 그린다 — `viewBox` 로 크기를 잡고, 선 · 글자는 `currentColor` 나 템플릿의 색 토큰을 써서 라이트 · 다크 모두에서 읽히게, `<svg role="img" aria-label="…">` 와 `<figcaption>` 에 그림이 말하는 것을 한 문장으로. 외부 스크립트 · 이미지는 쓰지 않는다.

- **결론 띠** — 머지 가능 여부 한 줄, 배포 전 필수 조건, 심각도별 개수
- **before/after 그림** — 1단계의 흐름을 같은 레인 · 같은 위치로 두 장 그린다. after 에서 새로 생긴 칸은 `n-new`, 바뀐 칸은 `n-mod`, 지적이 걸린 칸은 `n-warn` + 지적 번호. 화살표에 동사를 단다(`읽기` · `upsert` · `잠금`). 그림 아래 캡션에 "무엇이 바뀌었나" 를 두세 문장으로
- **영향받는 API 표** — 그림 바로 아래에 1단계에서 모은 API 를 한 줄씩: API(`메서드 경로` · 토픽) · 거치는 바뀐 칸 · 호출자에게 달라지는 것 · 걸린 지적 번호. 동작이 그대로인 API 도 바뀐 코드를 거치면 "달라지는 것 없음" 으로 넣는다. 하나도 없으면 표 대신 "없음" 과 무엇을 확인했는지 한 줄
- **여섯 관점 섹션** — 지적 카드: 심각도 · 제목 · 위치(`파일:줄` 또는 본문 문장) · 무엇이 어떻게 틀리는가 · 확인 방법(재현했으면 무엇으로) · 고칠 길. 관점에 지적이 없으면 "없음" 과 무엇을 확인했는지 한 줄
- **관점 기록 칸** — 관점 1 · 4 · 5 · 6 섹션의 접힌 표. 2단계 절차에서 본 것을 한 줄씩: 관점 1 은 주장 · 출처 · 맞춰 본 코드 · 결과, 관점 4 는 새로 더한 것 · 검색한 말 · 겹치는 것, 관점 5 는 테스트 · 뮤턴트 · 실행인지 읽기인지 · 결과(테스트가 없는 주장 · 새 코드는 테스트 칸에 「없음」), 관점 6 은 형제 · 공통점 · 새 코드에 있는지
- **질문 · 결정 필요**, **확인했고 문제없음**(접어 둠) — 반례 시도를 견딘 것만
- `<title>` 은 `PR #번호 리뷰` 처럼 짧게, 머리말에 PR 제목

## 지킬 것

- 작업 트리 · 브랜치를 바꾸지 않는다. 띄운 worktree · 컨테이너 · 임시 파일은 정리하고, 정리하지 못한 것은 페이지와 답에 적는다
- 운영 조회는 read-only 만
- PR 에 코멘트 · 승인은 사용자가 원할 때만. 올릴 때는 같은 지적이 이미 달렸는지 다시 본다
