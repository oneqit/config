# PR 리뷰 — 여섯 관점 + before/after 페이지

결과물은 **아티팩트 페이지 하나**다: 맨 위에 이 PR 이 코드의 동작을 어떻게 바꾸는지 before/after 그림, 그 아래 여섯 관점의 지적.
지적은 확인된 결함만, 지금 얼마나 아픈지와 고칠 길까지. 개수를 채우지 않는다 — 관점에 낼 것이 없으면 "없음" 한 줄.

## 1. 맥락과 흐름 파악 (직접)

- PR 본문 · 커밋 · diff, 프로젝트 지침(CLAUDE.md · 규약), 관련 **설계 문서**, 본문이 가리키는 연관 PR · 티켓의 실제 상태
- 이미 달린 리뷰 — 같은 지적을 또 내지 않는다. 다시 리뷰면 지난 리뷰 이후 커밋만
- **변경이 닿는 흐름**을 진입점 → 처리 → 저장소 · 외부 호출로 적는다. base 에서 한 번, head 에서 한 번. 이것이 before/after 그림의 재료이고, 2단계에서 "diff 밖 기존 코드" 를 어디까지 볼지 정한다
- 작업 트리를 바꾸지 않는다 — 다른 커밋은 `git show <sha>:<path>`, 실행은 스크래치 worktree

## 2. 여섯 관점

| # | 관점 | 핵심 질문 |
|---|---|---|
| 1 | **설계 · 본문 · 주석 ↔ 구현** | 설계 문서 · PR 본문 · 주석 · KDoc 이 말하는 동작과 숫자가 코드 · 설정과 같은가? 본문의 배포 · 복구 절차를 지금 코드로 따라가면 그대로 되는가? |
| 2 | **기능 구멍 · 버그** | 어떤 입력 · 순서 · 실패에서 틀린 결과 · 멈춤 · 조용한 누락이 나는가? 테스트가 그 규칙을 정말 지키는가? |
| 3 | **성능** | 지금은 괜찮아도 데이터가 10배 · 100배일 때 — 잠금 · 인덱스 · 쿼리 계획 · 메모리 · 타임아웃 · 반복 호출이 어떻게 되는가? |
| 4 | **중복 · 미사용 코드** | 같은 규칙이 여러 곳에 있거나, 변경으로 쓰이지 않게 된 코드 · 설정 · 테스트가 남았는가? **고칠 가치가 있는 것만** |
| 5 | **테스트 빈칸** | 바뀐 동작마다 유닛 테스트가 **정상 · 실패(예외 · 거부 · 재시도) · 엣지(빈 값 · 경계 · 중복 · 큰 입력)** 케이스를 갖췄는가? 빠진 케이스를 동작 단위로 적는다 |
| 6 | **더 맞는 패턴** | 레포의 기존 관용구에 더 맞는 모양이 있는가? 없거나 판단이 서지 않으면 쓰지 않는다 |

**근거의 기준** — 가능하면 로컬에서 재현한다(테스트 실행, 규칙 한 줄을 되돌린 뮤턴트, 컨테이너 DB 에 쿼리, 숫자는 직접 계산). 재현하지 못하면 코드 경로를 끝까지 따라간 근거를 적고, 코드 밖 사실에 달린 것은 질문으로 낸다. 어떤 방법으로 확인했는지를 지적마다 남긴다.

**"문제없음" 으로 닫기 전에** 반례를 하나 시도한다 — 같은 코드를 다른 각도(실패 경로 · 종료 신호 · 큰 데이터 · 동시 요청)로 한 번 더 본다. 이 판정이 가장 많이 틀렸다.

**나눠 보기** — 파일이 많거나 흐름이 여럿인 PR 은 관점 1 · 2 · 3(필요하면 4 · 5)을 서브에이전트로 병렬로 돌린다. 각자에게 1단계에서 적은 흐름 · 브리프 파일 경로 · 위 표의 그 관점 한 줄 · 근거의 기준 · 결과 파일 경로를 준다. 서로 다른 스크래치 경로를 주고, 재현에 띄운 worktree · 컨테이너는 지우게 한다. 관점 6 과 그림은 지휘자가 마지막에 직접 한다. 작은 PR 은 혼자 차례로 본다.

## 3. 심각도

| 표기 | 기준 |
|---|---|
| `높음` | 데이터 손실 · 권한 구멍 · 조용히 틀린 결과 · 정상 입력으로 오류 · 그대로 따라 하면 잘못 동작하는 운영 절차 · 다음 배포가 기동하지 못함 |
| `중간` | 지금 경로에서 조건만 맞으면 닿는 결함 · 문서 · 계약과 다른 동작 · 핵심 규칙을 지키는 테스트가 없음 |
| `낮음` | 아직 없는 기능 · 데이터 규모가 와야 닿는 결함 · 테스트 약점 · 틀린 주석 · 낡은 문서 |
| `선택` | 하면 좋은 정리 · 패턴 |
| `결정 필요` | 코드가 아니라 사람이 정할 것 |

머지를 막을 것(코드)과 배포 전에 할 것(본문 · 절차 · 인프라)을 구분해 결론에 적는다.

## 4. 결과 페이지

`assets/report-template.html` 을 스크래치 디렉터리에 복사해 채우고 Artifact 도구로 게시한다. 게시 전에 Artifact 도구가 요구하는 `artifact-design` · `artifact-diagramming` 스킬을 불러 그 규칙을 따른다.

- **결론 띠** — 머지 가능 여부 한 줄, 배포 전 필수 조건, 심각도별 개수
- **before/after 그림** — 1단계의 흐름을 같은 레인 · 같은 위치로 두 장 그린다. after 에서 새로 생긴 칸은 `n-new`, 바뀐 칸은 `n-mod`, 지적이 걸린 칸은 `n-warn` + 지적 번호. 화살표에 동사를 단다(`읽기` · `upsert` · `잠금`). 그림 아래 캡션에 "무엇이 바뀌었나" 를 두세 문장으로
- **여섯 관점 섹션** — 지적 카드: 심각도 · 제목 · 위치(`파일:줄` 또는 본문 문장) · 무엇이 어떻게 틀리는가 · 확인 방법(재현했으면 무엇으로) · 고칠 길. 관점에 지적이 없으면 "없음" 과 무엇을 확인했는지 한 줄
- **질문 · 결정 필요**, **확인했고 문제없음**(접어 둠) — 반례 시도를 견딘 것만
- 제목은 `PR #번호 리뷰` 처럼 짧게, 설명(`description`)에 PR 제목 한 문장

페이지는 비공개로 게시되지만 코드 조각과 사내 정보가 claude.ai 에 올라간다. 사용자가 원하지 않으면 로컬 HTML 파일로만 남긴다.

## 지킬 것

- 작업 트리 · 브랜치를 바꾸지 않는다. 띄운 worktree · 컨테이너 · 임시 파일은 정리하고, 정리하지 못한 것은 페이지와 답에 적는다
- 운영 조회는 read-only 만
- PR 에 코멘트 · 승인은 사용자가 원할 때만. 올릴 때는 같은 지적이 이미 달렸는지 다시 본다
